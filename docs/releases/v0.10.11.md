# AuraScan v0.10.11

Release date: 2026-09-30.

AuraScan v0.10.11 is a recovery-bearing release because it changes shared
scanning boundaries: the always-on repository-provenance link policy, the new
privileged-account rules, the reviewed runtime-intelligence wire contract, and
the upgrade advisory evidence all affect trust and handoff decisions that the
recovery runtime shares, and the architecture stabilization stages
restructured modules the recovery runtime uses. This record describes the
release candidate; publication remains blocked until the fresh recovery and
exact-ref release gates below pass and the tested image identity is pinned.

## Guided AUR update handling

- After the interactive repository-only continuation completes - or directly
  when it is declined or no repository packages remain - `aurascan upgrade`
  offers to handle each pending AUR update instead of leaving manual steps:
  download it from the canonical AUR URL through the trusted `git` boundary
  (validated name, shallow credential/hook/prompt-free clone, bounded runtime,
  exact-HEAD revision and a regular `PKGBUILD` required), review it with the
  standard scan (including the configured AI review), and - only after a
  passing review and a second consent - build and install it through
  `aurascan-makepkg --syncdeps --install`, then verify the installed version
  through trusted `pacman`.
- The new `--aurascan-scan-only` wrapper mode runs the same scan and
  classification (blocked, manual review, or pass) without recording a review
  acceptance and without invoking makepkg; the guided flow uses it to show a
  verdict before any build consent.
- Before asking to build, the guided flow reads the captured PKGBUILD's
  `depends`/`makedepends`/`checkdepends` declarations with a bounded literal
  parser (dynamic, malformed or function-scoped declarations disable the check
  silently) and classifies the missing ones with read-only trusted pacman
  queries. Dependencies the repositories can install are listed before the
  sudo-capable build step; dependencies pacman cannot install stop the build
  with the exact reason instead of running a doomed makepkg. This is what
  blocked `lib32-openal`: its `lib32-portaudio` makedepend is an AUR package,
  so `makepkg --syncdeps` could never install it.
- A missing dependency positively confirmed in the AUR can be downloaded,
  reviewed, built and installed first through the same consent-gated guided
  flow (recursive, limited to a chain of three), after which the original
  package continues to its build prompt. Parser doubt or a tool failure
  disables the check without making claims, and nothing in the check decides
  whether a build may run.
- Blocked or manual-review packages are never built by the guided flow, the AUR
  helper is never handed a build, and `--yes`/`--json` runs keep the plain
  guidance instead of prompts. The upgrade report now also shows the bounded
  reason when an AI review fails (for example a timeout) instead of only
  "error".

## Upgrade preflight continuation

- When `UPG-AUR-BUILD-UNSCANNED` is the only blocking preflight finding and at
  least one repository package is planned, interactive `aurascan upgrade` asks
  whether to continue with the documented repository-only transaction instead
  of ending at the blocked message. The continuation re-runs the preflight
  bound to `--aur-helper none`, hands only the repository part to pacman, and
  lists the pending AUR updates with the `aurascan-makepkg` build step for each
  one.
- The offer never clears the blocker, never invokes the AUR helper, and never
  installs an AUR update. Declining the offer, running with `--yes` or
  `--json`, dry runs, plans without repository packages, and runs with no
  interactive answer keep the unchanged hard stop, message and exit code.

## Finding explanations

- `AUR-REPO-INSPECTION-INCOMPLETE-001` names the first unsupported entry in the
  default report, for example
  `First unsupported entry: LICENSES/0BSD.txt (a symbolic link).` The detail is
  one bounded, sanitized checkout-relative path, so the reason and the location
  are visible without re-running the capture; the finding stays a HIGH
  fail-closed blocker.
- When an interactive non-JSON scan blocks, needs manual review, or reports
  HIGH/CRITICAL risk and AI is configured, `aurascan --pkgbuild`,
  `aurascan --pkg` and `aurascan-makepkg` (including the guided AUR review
  step) print one advisory explanation of what AuraScan observed or could not
  finish, why that stops the build or install, and where it happened. The
  prompt carries only fixed finding facts: paths, evidence snippets, hashes,
  raw output and anything naming the local home directory stay local. The
  response must be one strict bounded JSON object with a subset of the sent
  rule ids, and the explanation can never add or change a finding, severity,
  blocking decision or review state. A missing AI configuration prints
  nothing, provider failures and rejected responses print one fixed notice,
  and JSON output never includes the explanation.

## Repository provenance link policy

- Repository provenance now reads symbolic links with `readlink` and never
  follows them. A one-hop link is accepted only when its lexical target stays
  inside the checkout and was captured as a stable regular file; the link
  target bytes are bound into the checkout identity and the link joins the
  post-traversal revalidation. This removes the false blocker on ordinary AUR
  layouts such as the REUSE-style `LICENSES/0BSD.txt -> ../LICENSE` alias that
  stopped the `lib32-openal` review.
- Links that are absolute, escape the checkout, dangle, or point at
  directories, special files, pruned trees, or other links keep the fail-closed
  HIGH `AUR-REPO-INSPECTION-INCOMPLETE-001` result, now with the sanitized
  `link -> target` detail. A link that changes type or target during capture
  fails closed as `symlink_changed`.
- `REPOSITORY_SNAPSHOT_VERSION` advances to `1.3` and the package-scanner rule
  version advances from `1.10.0` to `1.12.0` so cached reports are
  re-evaluated; the scanner version remains `2.6.0`.
- README now states explicitly that a clean result is not a sandbox and
  recommends a disposable local virtual machine for hands-on testing of a
  package that still looks hostile after review.

## Detection and advisory coverage

- `PRIV-ACCOUNT-BACKDOOR-001` is a CRITICAL blocking correlation: the same
  package-controlled text sets an account password to a literal value, grants
  that account privilege, and exposes SSH. It catches a remote root-equivalent
  login assembled from ordinary account, sudo and SSH facilities, with no
  downloader, obfuscation or embedded payload to detect.
  `PRIV-ACCOUNT-CREDENTIAL-001` reports the literal-credential behavior alone
  as HIGH needing review, `PRIV-SUDO-ADMIN-GROUP-001` reports an
  administrative-group sudo policy that does not use `NOPASSWD`, and
  `DEEPSTATIC-PRIV-ACCOUNT-BACKDOOR-001` covers the same chain in acquired
  source. The credential half is read only from shell command position, and
  ordinary locked service accounts stay negative cases. Evidence labels are
  fixed strings, so the observed account name, password, hash and policy line
  never appear in a report; the motivating 2026-09-14 aur-general report about
  the removed `x11-qemu-validation` package is cited without re-encoding
  unverified third-party details.
- A vendor advisory record may declare reviewed `derived_packages` (for example
  `ungoogled-chromium` or `librewolf`). When one is installed,
  `SEC-VENDOR-ADVISORY-DERIVED-PACKAGE-UNMAPPED` reports MEDIUM that the
  upstream floor cannot be evaluated for it. No version comparison is
  performed and the finding never claims exposure. Undeclared lookalike names
  still produce nothing, and a pending update of that exact package suppresses
  the note from the upgrade summary while the installed-state audit keeps it.
- Vendor advisories now record the vendor's own severity and an explicit
  exploitation state, with a comparator declared per entry
  (`chromium_four_part` or the new `numeric_dotted_upstream`).
  `SEC-VENDOR-SECURITY-FLOOR-LAG` is the new HIGH rule for a verified vendor
  floor whose exploitation is not established, and
  `SEC-KNOWN-EXPLOITED-VERSION-LAG` keeps the exploited case. Added `chromium`
  below `153.0.8010.47`, `firefox` below `156.0` and `thunderbird` below
  `156.0`, reviewed on 2026-09-16 with no exploitation evidence. Floors map to
  exact Arch package names, so browser forks are never matched by version
  similarity. The runtime-intelligence wire contract moves to schema and
  engine capability `2.0`; a `1.0` payload, manifest or stored generation is
  rejected rather than reinterpreted, and a `1.0` detection is never carried
  over silently. The general-purpose security-audit report schema is unchanged
  at `1.0`.
- `aurascan upgrade` now evaluates installed-version advisories from captured
  local package evidence instead of a placeholder value. An installed package
  below a verified advisory floor now raises the existing HIGH
  `SEC-KNOWN-EXPLOITED-VERSION-LAG` finding and can require the normal
  high-risk confirmation, where the earlier placeholder evidence could only
  produce MEDIUM unresolved coverage. Missing, invalid, conflicting, oversized
  or unqueryable version evidence keeps the existing
  `SEC-VENDOR-ADVISORY-VERSION-UNRESOLVED` unresolved-coverage outcome for that
  installed name. Installed versions are what the local pacman database
  reports; they do not authenticate package origin, repository integrity, or
  downstream backport equivalence.

## Deep-static Git signature evidence (observational)

- Explicit `--deep-static` acquisition now reports the signature state of the
  exact Git object it resolved: the local object type (annotated tag,
  lightweight tag or commit), whether a signature is present, its format, a
  verified signer fingerprint, and whether that fingerprint matches a declared
  `validpgpkeys` entry. The previous finding text that said signed tag
  verification was not implemented is replaced.
- Validity is decided by Git's own `verify-tag`/`verify-commit` with the
  trusted absolute Git and GnuPG files, a private temporary GnuPG home,
  locally available key material and a bounded deadline. Only machine-readable
  `VALIDSIG` status can establish a signer fingerprint, and an older Git
  without machine status leaves the fingerprint unavailable rather than
  guessing one.
- Declared correlation is reported separately from cryptographic validity. An
  undeclared signer is never trusted, an invalid signature is reported
  distinctly without blocking, and expired or revoked signing-key status is
  never presented as an ordinary valid declared signer. Unsupported formats
  (SSH/X.509), missing keys and unavailable verifiers stay explicit unresolved
  coverage instead of "unsigned".
- Signature evidence is observational: it never changes acquisition status,
  blocking policy, rule IDs, AI authority or the network/privilege surface,
  and it never establishes signer authorization, official origin, source
  safety, review or an uncompromised upstream. Verification performs no
  implicit key retrieval, so it works offline when key material is already
  available.

## Build handoff hardening

- `PRIV-BUILD-PRIVILEGE-ELEVATION-001` is a CRITICAL blocker for `sudo`,
  `doas`, `pkexec`, `su` and `run0` in package build logic, and for the
  non-`sudo` family in install hooks. `sudo` in an install hook keeps its
  existing `EXEC-INSTALL-HOOK-SUDO-001` rule, and only
  `sudo -u <non-root user>` keeps the narrow justification. A build step that
  tries to escalate never reaches makepkg, so a cached sudo timestamp cannot
  be used by it.
- Immediately before the makepkg handoff the packaged entry point now clears
  the operator's cached sudo timestamp with the trusted absolute `sudo -k`.
  The step reports rather than blocks, because a user who may not run sudo has
  no cached timestamp to remove; the JSON envelope carries
  `sudo_cache_invalidation` (`not_requested`, `absent`, `invalidated`,
  `unconfirmed`, `untrusted`) and an unconfirmed step adds a warning instead
  of failing the build. The hygiene step is requested only by the real entry
  point; `run()` defaults to a no-op seam, so an in-process or test caller can
  never clear a developer's credentials as a side effect.

## Review adjudication capture

- Review acceptances now also capture a local, append-only record that binds
  the operator's judgment to the exact PKGBUILD, install-hook and
  source-metadata hashes, the scan fingerprint, the finding identities and the
  scanner, rule and intelligence provenance. Capture is best effort: it can
  never block a scan, a review acceptance or a build.
- The judgment is an allowlisted label supplied with
  `--aurascan-adjudication` (`benign_false_positive`,
  `benign_expected_behavior`, `suspicious_unconfirmed`,
  `confirmed_malicious`). Without a label the record stays unlabeled, which is
  not a training target, and an unrecognized label is rejected instead of
  being silently dropped. Free-text review reasons are never copied into the
  record, and a revocation or relabel supersedes the earlier judgment while
  the original stays in the log.
- `aurascan evidence status` reports capture counts, labels and consent state;
  `aurascan evidence consent --purpose P --confirm P` records consent for one
  named purpose (`analysis`, `training`, `commercial_training`,
  `redistribution`), and consent for one purpose never authorizes another;
  `aurascan evidence export --purpose P --out FILE` writes quarantine
  candidates and refuses without that consent or without labeled records.
- Exported candidates are never admitted: they carry `partition: quarantine`,
  `admission: not_admitted`, unresolved rights for every purpose, a hash-only
  content binding and a derivation-family token. Raw package bytes, host
  paths, operator identity and free-text notes are excluded, so binding real
  content stays a separate offline intake step under its own consent and
  admission review. Nothing on this path can admit data, grant rights, choose
  a split, contact a network, or train a model, and AI credentials are not
  read.

## Architecture stabilization (no behavior change)

- The fourteen architecture stabilization stages are closed. Terminal
  rendering left the core evidence model and the last self-rendering report
  classes into presentation modules; the inert upgrade values moved into
  `core/upgrade_models.py`; incident vocabulary, redaction, private-state
  writes and bounded command capture moved to dedicated owners; the follow-up
  framework lost every concrete lifecycle adapter and workflow import in favor
  of caller-supplied providers; and the privileged mirrorlist restore and
  revalidate-then-run helper moved to `core/repository_repair.py` and
  `core/trusted_executable.py`.
- `tools/architecture_audit.py` reports module responsibilities, coupling,
  side-effect capabilities, import cycles and nineteen enforced architecture
  invariants with `--strict` and `--json` modes, and `docs/ARCHITECTURE.md`
  records the stabilized baseline. Moved functions are AST-identical to their
  previous definitions, rendered output stays byte-identical under full golden
  tests, and no user-visible behavior changes on this path.

## Recovery distribution and validation

`aurascan-recovery-0.10.11-x86_64.iso`, distributed together with its
`.iso.sha256` sidecar and sorted `.iso.packages.txt` manifest. The ISO must be
strictly smaller than 2 GiB (2,147,483,648 bytes). It must come from a clean
committed candidate in a freshly provisioned disposable Arch VM with externally
bounded CPU, RAM and disk, fresh trusted work/output roots, no host shares and
no release credentials. Locally built UKIs are kernel/key-specific validation

## Limits

No scan, guided review, dependency pre-check or AI explanation proves that a
package is safe. A passing review only means AuraScan did not find the signals
it checks; a guided build still runs package code on this machine through
makepkg after explicit consent, and an in-checkout link policy result says
nothing about file authorship or intent. The finding explanation is advisory
display text and can never lower, add or clear a deterministic result.

A valid signature authenticates the configured publisher, not the accuracy of
an indicator, execution of package behavior or absence of compromise. This is
not a complete malware/CVE feed or a TUF implementation. Offline freshness
cannot reveal unseen newer releases or authenticate the host clock. Publisher
mistakes, key compromise, native-parser flaws and privileged host compromise
remain risks; key replacement or compromise recovery requires an application
update in this version. Normal scanning and Instruction Guard stay
non-fetching, and no scan data, project configuration or AI credentials enter
the updater. Production feed and signing keys remain unconfigured; provisioning
them requires a separately reviewed application release.
