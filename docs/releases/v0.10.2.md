# AuraScan v0.10.2

Released on 2026-09-01.

## AUR Repository Artifact Provenance

- This generic provenance control responds to the package-inspectability issue
  discussed in the [31 August 2026 aur-general report about packages shipping
  precompiled binaries](https://lists.archlinux.org/archives/list/aur-general%40lists.archlinux.org/thread/HI6AJSU7LMGWOELAI2JUABEMNVHPGBAG/).
  The report explicitly did not allege that the named packages were malicious;
  AuraScan likewise reports observable provenance and static use rather than a
  confirmed compromise.
- AuraScan now takes an always-on, bounded, no-follow snapshot of regular files
  beside the PKGBUILD before source acquisition, cache reuse, review, or allow
  decisions. It classifies supported ELF, PE, Mach-O, and opaque archive magic
  from stable bounded bytes without invoking Git, extracting archives,
  contacting a network, or executing package content.
- `AUR-REPO-OPAQUE-ARTIFACT-001` requests MEDIUM, non-hard-blocking,
  acceptance-eligible manual review for an undeclared opaque artifact whose
  presence is the only evidence.
  `AUR-REPO-OPAQUE-BINARY-001` requests HIGH manual review when package logic
  contains a supported request to copy, move, extract, or install the exact
  artifact into `$pkgdir`.
  `AUR-REPO-OPAQUE-BINARY-EXEC-001` is CRITICAL and blocking only when the
  package text contains a supported exact request to invoke or code-load the
  artifact or its proven staged destination, or assign SUID/SGID permissions.
- A statically declared local `source=()` file remains under normal source
  provenance and does not trigger the repository-embedded rule. A normal
  binary-distribution package that declares its upstream HTTPS archive with a
  fixed checksum is not flagged merely because the acquired archive is binary.
  Uninstalled icons, firmware, fonts, fixtures, and other opaque data do not
  become blockers from file type alone.

## Fail-Closed Identity And Handoff

- `AUR-REPO-INSPECTION-INCOMPLETE-001` is a HIGH, non-reviewable blocker when
  bounded traversal, stable capture, source mapping, or command correlation
  cannot complete. It describes missing inspection coverage, not malware.
- Repository snapshot identity now participates in cache keys, history, trust
  diffs, review fingerprints, and makepkg-wrapper revalidation. A binary-only
  replacement therefore cannot reuse a prior clear result while the PKGBUILD
  stays unchanged.
- The wrapper performs a final full-input recapture, refuses makepkg options
  that substitute or reuse unscanned inputs or skip integrity verification,
  and removes shell or dynamic-loader code-loading variables before handoff.
  The handoff still runs package build logic and is not a sandbox.
- Verbose local review shows the sanitized control location and one-based line,
  or the observed relative path for a presence-only finding, plus a 12-character
  artifact SHA-256 prefix. Artifact bytes and matched command text are neither
  printed nor persisted as evidence.

## Evidence Limits And Compatibility

- “Repository” means the bounded filesystem checkout beside the PKGBUILD.
  AuraScan does not invoke Git and cannot prove that a file was committed,
  distributed through the AUR, installed, successfully executed, or malicious.
  Unsupported or disguised formats and runtime-only control flow can remain
  opaque; a clear result is not proof of safety.
- The application and Arch/AUR package advance to v0.10.2. Package-scanner rule
  version advances from `1.4.0` to `1.5.0`; scanner version remains `2.5.0`.
  Repository snapshot version starts at `1.0`, package scan-input version
  advances to `2.0`, and Instruction Guard report schema and rule version
  remain `1.0`.
- CI keeps package and Instruction Guard AI disabled, never scans the real home,
  and does not execute Git, makepkg, fixture commands, package content, or live
  provider/network workflows in these regression tests.
