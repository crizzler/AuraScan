# AuraScan v0.10.3

Released on 2026-09-01.

AuraScan v0.10.3 is a recovery-bearing release. It refreshes the optional
hybrid recovery image for the first time since v0.6.0 and makes recovery
artifact disposition an explicit part of every future release.

## Recovery Distribution

- The release publishes one indivisible, version-matched artifact set:
  `aurascan-recovery-0.10.3-x86_64.iso`, its `.iso.sha256` sidecar, and its
  sorted `.iso.packages.txt` manifest. The tested ISO SHA-256 is pinned here
  and in the packaged recovery manifest.
- AuraScan's strict `aurascan_recovery_iso/2.0` packaged manifest distinguishes
  a release-ready image from a build-required placeholder and validates its
  exact fields, architecture, version, filename, URL, and digest before
  offering a download. The legacy six-field `1.0` document is rejected rather
  than silently reinterpreted. Doctor and recovery status expose that state
  rather than describing any syntactically plausible old URL as current.
- Recovery remains optional. Installing or upgrading the Arch package neither
  writes an ESP nor enables a boot entry. Locally built UKIs remain specific
  to the host kernel, bootloader, and Secure Boot owner keys and are not
  published as universal release assets.

## Bounded Release Identity

- Recovery ISO construction now requires a clean committed candidate, fresh
  work and output locations, the exact expected ISO filename, and trusted
  absolute build tools under a sanitized environment. A stale ISO cannot be
  selected from a previous build directory.
- The recorded commit, artifact digests, and sorted installed-package manifest
  bind validation to one candidate; they do not make the image bit-reproducible.
  Archiso still resolves the then-current signed packages from configured Arch
  repositories, so rebuilding later can produce different bytes.
- The builder emits a deterministic checksum sidecar and sorted package
  manifest and rejects a GitHub release asset at or above 2 GiB. Its bounded
  artifact audit checks the expanded image material for credential assignments
  with bounded values, known provider-token prefixes, explicitly supplied
  private markers, known developer/build paths, persistent host identity, and
  known private-state locations. It applies path policy to files, directories,
  and normalized link destinations and scans bounded entry/owner/PAX metadata
  plus decoded libarchive xattrs. Short explicit or host-identity markers fail
  closed. It neither loads arbitrary secret stores nor treats opaque compressed
  bytes as proof that nested content was inspected.
- A release is now declared either `recovery-bearing` or `package-only`.
  Changes to the recovery runtime, its shared AI/provider security boundary,
  recipes, boot integration, dependencies, or image tooling require a matching
  recovery-bearing release. A package-only release must name the retained
  image and state that recovery image gates were not rerun.
- The manifest records the image release date. Runtime uses the UTC calendar
  and accepts at most one day of bounded clock skew without producing a
  negative image age; a materially future date remains invalid. Doctor warns
  after 90 days, and a new package-only release cannot retain an image beyond
  that window; the date cannot be advanced without building and validating new
  ISO bytes.

## Safety Boundaries

- ISO and UKI creation use AuraScan's own trusted release tree; the workflow
  does not execute third-party PKGBUILDs, package samples, agent instructions,
  or fixture commands. General (`AURASCAN_AI_ENABLED`), Instruction Guard
  (`AURASCAN_INSTRUCTION_AI_ENABLED`), Incident
  (`AURASCAN_INCIDENT_AI_ENABLED`), and Recovery
  (`AURASCAN_RECOVERY_AI_ENABLED`) AI stay disabled during build and
  validation, with provider credentials removed from the build environment.
- A digest proves byte identity, not that every recovery action is safe.
  Recovery AI remains separately consented, tool-free for command creation,
  and subordinate to deterministic diagnostics and independently validated
  repair recipes.
- Secure Boot testing uses disposable test keys. AuraScan does not enroll
  owner keys, change authentication policy, repartition storage, perform
  automatic filesystem repair, delete user data, or reboot automatically.
- The Secure Boot negative control binds its signature-stripped UKI to the
  builder-attested unsigned image with a bounded x86-64 PE32+ parser. Only the
  Optional Header's four-byte `CheckSum` may be recomputed; file size and every
  other byte must match, and reattaching the detached signature must reproduce
  the exact signed input.
- Fixed tool paths and bounded artifact inspection reduce release risk but are
  not a sandbox. A compromised builder, package repository, firmware, root
  account, or native parser can still defeat the release process.
- Recovery USB writing now uses bounded, revalidated absolute `findmnt` and
  `lsblk` probes, refuses malformed or incomplete probe output or an
  uncorrelated running root, repeats eligibility after typed confirmation and
  while the exclusive descriptor is held, and requires the same positive
  `DISK-SEQ` at all three inspections. It binds the inspected kernel major/minor
  number to the final no-follow device descriptor before writing and
  verification.

## Compatibility And Versioning

- The application and Arch/AUR package advance to v0.10.3. Scanner version
  remains `2.5.0`, package-scanner rule version remains `1.5.0`, repository
  snapshot version remains `1.0`, package scan-input version remains `2.0`,
  and Instruction Guard schema and rule version remain `1.0`.
- The v0.6.0 recovery image remains an immutable historical asset. The v0.10.3
  image is published under the new tag; no previous release or tag is
  rewritten.
